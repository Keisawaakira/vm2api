# cacheIssue-1.3.89：五条请求的缓存与额度记录

调查日期：2026-10-02。输入为用户提供的 `logs/cacheIssue-1.3.89/` 五个原始 JSONL，未修改或重放真实推理。基线 `test@4c0e211`（相对 `8fff5c2` 只删除两份历史 v186 CLI）。完整哈希、元数据提取、生产解析器重放和官网快照在 `Temp/vm2api-cache-issue-20261002/`。本文是这组样本的调查证据，不是订阅计费公式或云端效率认证。

## 结论

本组记录不支持“新缓存机制让每次都按未命中处理”。第一条是约20.68万 tokens 的整段1h缓存写入；后四条读取了97.04%～99.995%的输入。上游额度头的同窗快照为0%→35%→41%→47%→51%，大跳变集中在冷写与下一次响应之间，不能用用户观察的约52%除以5来证明每条暖请求都扣约10%。

这不是根因已完全关闭：头部是快照，不是逐条结算单；缺少有效的 CC 出站记录，无法排除未见的 CLI 请求；官方没有给出可用此表反算的固定5h-dollar/token公式，也不能据此排除账户/服务端额度变化。

## API价估算与5h额度必须分开

生产 `request-log.mjs` 的 `actual_cost` 是本地 `total_cost × rate_multiplier`，不是收到的 Anthropic 账单。Opus4.6 当前公开 API 价为输入5、输出25、1h写10、缓存读0.5美元/百万 tokens；同价组内部叫 `opus-4.5`，不是把运行模型换到4.5。

本地重算与五条存储字段全部一致：第一条约$2.273125（其中写缓存$2.0683），后四条约$0.3713/$0.361294/$0.294486/$0.2828865。五条合计$3.5830915，第一条占本组估算63.44%。这说明冷写为什么能显著抬高平均数；**不能把这些美元按比例换算成官方5h百分比**，也不覆盖未观测的其他 API 请求。

“没有命中并建立1h缓存”也不同于“不建缓存的普通输入”：API价表中1h写为基础输入价的2倍，读为0.1倍。该区别不是本轮新增：旧9月26/27日志已明确写入1h，非这次从5m改为1h。

## 尚缺的原生证据

所有 `native_trace` 都是 `unavailable/native_trace_not_observed`，票据仍 pending；仅有14:35:53Z更新的PID41旧快照，`hook_current:false`、只见一条无nonce任务。它不属于这五条请求的可验证归属，不能证明当前实际 CLI 的 PID/版本，也不能当作云端“0次请求”。

因此先核对请求实际 VM 的原生跟踪就绪状态和 live CLI PID，无需再花额度生成长回复。不要用旧快照猜当前进程；不能从 kernel SSE 补造 CC→API 的正文、重试次数或结算明细。后续自然请求有完整 native_trace 时，再核对每次真实 API 请求/响应与额度头。
